## Decisions taken

- **Режим виконання: multi-agent** — *human-answered* («Execution mode: multi-agent — заявлено користувачем»). Конвеєр `/implement`: implementer (кілька паралельно за власністю файлів) → architecture-reviewer ∥ /code-review ∥ /security-review → fix loop → plan-verifier → doc-writer → /pr-self-review.
- **Спека `approved`** — *human-answered* («Status: approved — людина щойно підтвердила»). Планую проти неї як проти джерела вимог; жодного критерію не дописую.
- **Дефолти Open questions спеки прийнято як мої дефолти** — *default-assumed* (за вказівкою делегації «бери дефолт спеки як свій дефолт»):
  1. «не більше 5 пунктів Review Focus і не більше 5 ризиків, решта відкидається на боці сервера до збереження»;
  2. «нести `line` як необов'язкове значення й використовувати його лише для тексту пункту, а перехід робити по файлу»;
  3. «обидва [GET і POST], бо картка на вкладці Overview читається при кожному відкритті сторінки»;
  4. «із `GET /pulls/:id/reviews`, беручи перший рядок із `kind = 'review'` … без нового поля на дроті»;

## Constraints that bind this change

- **Чи щось перетинає дріт?** Так. `PrWhyBrief` — новий wire-контракт. Обидві копії `@devdigest/shared` рухаються **одним кроком** (крок 1): `server/src/vendor/shared/contracts/brief.ts` (канонічна) і `client/src/vendor/shared/contracts/brief.ts` (обрізана). Барелі реекспортують через `export *` (`vendor/shared/index.ts:19`), тож змінюється лише шапка-коментар (обидві копії, той самий крок). Наявний `PrBrief` не чіпаємо (AC-42).
- **Контракти Zod-first.** Одна схема валідує `params` і серіалізує відповідь; `Schema.parse(req.body)` у хендлері не буде. Тіла в POST немає взагалі, тож `body` не оголошуємо (інакше `null`-пастка `server/INSIGHTS.md:199-207`). Схема для провайдера (`BriefDraft`) — **окрема чернетка модуля**, не wire-контракт (NFR-8, AC-15).
- **Міграції.** Потрібна одна **нова** міграція: `pr_brief` + `head_sha text`, `generated_at timestamptz`, `model text` — усі nullable, лише `ADD COLUMN` (AC-23, AC-24). Застосовані `server/src/db/migrations/*.sql` не редагуються. Генерація: `cd server && pnpm db:generate` (дифф лише додає → інтерактивного промта `drizzle-kit` бути не має, root `INSIGHTS.md:137-141`); застосування: `cd server && pnpm db:migrate` — на буті не запускається. Індексів не додаємо: доступ лише за `pr_id` (первинний ключ, B-tree уже є).
- **Тестова смуга.** Усе, що торкається Postgres, — `server/test/brief.it.test.ts`; чисті функції (`facts`, `helpers`, grounding, промт) — звичайні `*.test.ts` у юніт-смузі. Жодного DB-тесту без суфікса `.it.test.ts`.
- **Пакетний менеджер по кроках.** `server/`, `client/` → **pnpm**; `e2e/` → **npm**. Установка в корені не робить нічого.
- **`reviewer-core` не емітить JS** — і цією зміною не зачіпається взагалі (жодного файла в `reviewer-core/`).
- **Do-not-touch шляхи.** `server/clones/**` — не чіпаємо (документи Project Context читаються **лише** через `container.projectContext`, який уже має захищений читач). Застосовані міграції — не чіпаємо, додаємо нову. `**/src/vendor/ui/**` — не чіпаємо; якщо картці забракне примітива UI-кіту, це **не** підстава правити vendor: беремо наявні примітиви (`root INSIGHTS.md:67-78` — рядок vendor/ui взагалі не виконуваний агентом).
- **Шарування.** Зачіпається. Новий модуль `server/src/modules/brief/{routes,service,repository,facts,helpers,constants,types}.ts` + один рядок у `src/modules/index.ts`. Жодного імпорту чужих `service.ts`/`helpers.ts` (`no-cross-module-internals`). Тестовий шов — `ContainerOverrides` (`{ blast, projectContext, github, llm }`), не `vi.mock`.

## Contract & migration impact

**Що перетинає дріт.** Новий `PrWhyBrief` у `contracts/brief.ts` — **обидві копії в кроці 1**, наявний `PrBrief` не змінюється. Барелі реекспортують через `export *`, тож нового рядка експорту не потрібно — лише шапка-коментар (`index.ts:6`) в обох копіях. Сьогодні копії ідентичні; крок 8 має тест, який тримає їх такими.

Форма (значення кожного поля закріплене тут, щоб дві смуги не реалізували його по-різному):

- `what: string` — суть зміни; `why: string` — мотивація. Ніколи не переказ заголовка PR (AC-17). Обидва — **недовірений текст моделі**, рендеряться екранованими (AC-44).
- `risk_level: RiskSeverity` — той самий enum, що в `Risk.severity` (`high`/`medium`/`low`), нового не заводимо (AC-22).
- `risks: Risk[]` — наявний `Risk` без змін. `file_refs` — **лише шляхи, що були у вхідних фактах** (AC-18); endpoint, згаданий у тексті ризику, має існувати в `endpoints_affected` карти blast (AC-19). Максимум 5 (Open questions, дефолт спеки).
- `review_focus: ReviewFocusItem[]`, `ReviewFocusItem = { path: string; reason: string; line: number | null }`. **Значення `path` і `line` різне за призначенням і це найважливіше місце контракту:**
  - `path` — **тільки** шлях зі списку змінених файлів цього PR (AC-20). Це і ціль переходу: клієнт кладе його в `?file=` і відкриває саме цей `FileCard`. Модель не може відправити користувача на файл поза дифом.
  - `line` — **лише текст пункту**, ніколи не ціль переходу і ніколи не якір. Причина: рядки з blast резолвляться проти `indexed_sha`, а не `head_sha` (root `INSIGHTS.md:80-90`), тож той самий `file:line` у вкладці змін відкриє чужий рядок. `null` означає «модель не назвала рядок», не «рядок 0».
  - `reason` — недовірений текст моделі, екранований при рендері.
  - Порожній масив — валідний і очікуваний стан (AC-21), не «помилка» і не «ще не готово».
- `inputs: BriefInput[]`, `BriefInput = { type: 'intent' | 'blast' | 'diff' | 'linked_issue' | 'context_doc'; ref: string | null; status: 'used' | 'unavailable' | 'partial' | 'degraded' }`. **Значення `ref` і `status` різне за `type`** — записано по варіантах, бо саме такі поля дві смуги реалізують по-різному:
  - `intent` — `ref: null`; `status` `used` або `unavailable` (AC-8).
  - `blast` — `ref` = `indexed_sha` або `null`; `status` `used` | `partial` | `degraded` — **єдиний варіант, де `partial`/`degraded` легальні** (AC-9), і саме він забороняє картці стверджувати «ні на що не впливає».
  - `diff` — `ref: null`; `unavailable`, коли `pr_files` порожні (PR, який ніхто не відкривав, `server/INSIGHTS.md:106-114`).
  - `linked_issue` — `ref` = `#<number>` як рядок; `unavailable`, коли issue немає або GitHub не відповів (AC-10).
  - `context_doc` — **по одному запису на документ**, `ref` = repo-relative POSIX-шлях; `used` для тих, що потрапили в промт, `unavailable` для відкинутих лімітом (AC-12) або нечитних (AC-13). Це те місце, де «мовчки для моделі, але видимо в `inputs`» стає перевірним.
- `head_sha: string` — коміт, на якому brief побудовано; `generated_at: string` (ISO); `model: string | null`.
- `stale: boolean` — **обчислює сервер** при кожному читанні, порівнюючи `pr_brief.head_sha` з поточним `pull_requests.head_sha`. Клієнт його не рахує (інакше дві реалізації розійдуться), лише показує (AC-26, AC-40).
- **Чого в контракті немає і не буде:** `score` (єдине джерело істини — `reviews.score`, AC-54), токени, вартість, провайдерський ключ (AC-46, NFR-4).
- `GET /pulls/:id/brief` віддає `PrWhyBrief | null`; `POST /pulls/:id/brief` — завжди `PrWhyBrief` (або помилку, AC-16). Тіла запиту в POST немає.

**Міграція.** Одна нова, суто додавальна (крок 2):

- `pr_brief.head_sha text` (nullable — рядки з-перед цієї фічі його не мають), `pr_brief.generated_at timestamptz`, `pr_brief.model text`.
- Генерується `cd server && pnpm db:generate` → `0017_*.sql`; застосовується `cd server && pnpm db:migrate` (на буті не запускається). Дифф лише додає, тож інтерактивного промта `drizzle-kit` бути не має — якщо він з'явився, у дифі є ще щось (root `INSIGHTS.md:137-141`).
- Нових таблиць і нових індексів немає: доступ виключно за `pr_id` (PK).
- Сумісність назад: рядок без `head_sha` читається як «застарілий невідомого походження» — сервіс віддає його зі `stale: true`, а не 500 (нинішня таблиця порожня, тож це суто оборонний шлях).

## Risks

- **`pr_files` порожні для PR, який ніхто не відкривав** → факти diff порожні, `review_focus[]` порожній, і це виглядає як «фіча не працює» (`server/INSIGHTS.md:106-114`). Найдешевший ранній сигнал: у `brief.it.test.ts` кейс «PR без жодного рядка `pr_files`» має віддати `inputs` із `diff: unavailable`, а не мовчазну порожнечу.
- **Інтеграційний тест дістає реальний провайдер.** `risk_brief` за замовчуванням `openai`, а `container.llm` падає через `secrets.get()` у `process.env`, де на машині розробника лежить справжній ключ (`server/INSIGHTS.md:266-286`). Сигнал: тест «висить» ~10 с і в stderr зʼявляється попередження справжнього `openai` SDK. Профілактика: мокати слот `openai` (за ключем override, не за `.id` мока) у кожному тесті кроку 8.
- **`strict: true` відхиляє схему чернетки** через `.optional()`/`z.record` (root `INSIGHTS.md:31-41`). Сигнал дешевий і ранній: юніт-тест кроку 8, що обходить `BriefDraft` і падає на будь-якому `optional`, — до першого реального виклику.
- **Перехід у файл «недольотує»**: скрол відпрацював, а сусідні `FileCard` розгорнулись після нього й посунули ціль (`client/INSIGHTS.md:73-83`). Сигнал: e2e крок 13 бачить `?file=` в URL і розгорнутий файл, але людина в браузері бачить не той файл на екрані — тобто RTL і e2e тут не ловлять; перевірити руками в кроці 14.
- **Дві смуги розійдуться на `inputs[]`/`stale`** — типово це не typecheck-помилка, а різне тлумачення варіанта (`context_doc` по документу vs один агрегований рядок). Сигнал: крок 14 звіряє живу відповідь із рендером; секція **Contract & migration impact** написана так, щоб суперечку можна було закрити цитатою.
- **e2e-флоу випадково витратить гроші**, якщо хтось додасть клік по кнопці регенерації. Сигнал: `./scripts/e2e.sh` починає потребувати ключ / падає без нього. Правило записане в кроці 13 явно.
- **Сіяний `pr_brief` розійдеться з контрактом** після майбутньої зміни форми — і флоу 12 впаде «на порожньому місці». Пом'якшення: сервіс парсить збережений `json` через `safeParse` і поводиться з нечитним рядком як із відсутнім (прецедент `parseStoredTour`, `onboarding/service.ts:57-71`).

1. **Скільки максимум пунктів у `review_focus[]` і скільки ризиків показує картка?** — дефолт (зі спеки): не більше 5 пунктів Review Focus і не більше 5 ризиків, решта відкидається на боці сервера до збереження.

3. **`GET` + `POST` чи лише `POST`?** — дефолт (зі спеки): обидва.
4. **Звідки картка бере оцінку?** — дефолт (зі спеки): із `GET /pulls/:id/reviews`, перший рядок із `kind = 'review'`, без нового поля на дроті.
5. **Чи позначати оцінку, отриману на старішому `head_sha`, як застарілу?** — дефолт (зі спеки): ні.
6. **Що зі збереженим brief, коли ключ моделі для `risk_brief` змінили в Settings?** — дефолт (зі спеки): нічого; застарілість визначає лише `head_sha`.
7. **Як саме читати «спільний каталог-префікс» в AC-11?** — дефолт (мій, бо спека формулює предикат словами): документ релевантний, якщо його шлях і шлях якогось зміненого файла мають **щонайменше один спільний ведучий сегмент каталогу**; документ у корені репозиторію релевантний лише тоді, коли в дифі є файл у корені. Корінь репозиторію спільним префіксом не вважається (інакше релевантні всі документи). Змінює лише предикат однієї чистої функції `relevantContextDocs` (крок 5) — кроків, файлів і смуг не змінює.
8. **Ім'я query-параметра для адресації файла.** — дефолт: `?file=<repo-relative POSIX path, URL-encoded>`, поруч із наявними `?tab=`/`?finding=`/`?severity=`; пишеться тим самим `setParams` одним оновленням.
